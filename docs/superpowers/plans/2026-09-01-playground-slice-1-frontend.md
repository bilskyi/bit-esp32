# Playground Slice 1, Frontend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The thing you can actually open. A logged-in web app served by the
existing FastAPI service: streaming chat with a per-message inspector showing
what each turn really did, a settings surface for roles, mood, memory and
recording, and the device's own eyes mirrored in the browser.

**Architecture:** One Railway service, one process. FastAPI keeps the WS
protocol and the JSON API and additionally serves a built React+Vite bundle at
`/`, same origin, so the session cookie needs no CORS. The static mount is
registered last with an SPA fallback that must not shadow API 404s. Nothing
about the ESP32's path changes.

**Tech Stack:** React 18 + Vite + TypeScript, no UI framework and no CSS
framework (the design language already exists — see Design below), `npm` for
the frontend, `uv` for the backend, a two-stage Dockerfile replacing nixpacks.

## Global Constraints

- **`server/persona.py` must not be touched.** `BASE` is a measured LLM prompt;
  `tests/test_persona.py`'s golden test asserts the assembly reproduces it byte
  for byte.
- **The ESP32's path must not change.** `_token_ok` and the bearer branch of
  `_authorise_connection` stay exactly as they are. No new frame type may reach
  a connection whose surface is `"esp32"`.
- **Do not reimplement the eyes in JavaScript.** `firmware/host/face_preview.c`
  says why in its own header: "neither was reimplementing the eyes in
  JavaScript — the copy drifts from the original within a day." The web face is
  generated from `firmware/main/face.c` by a build step. This is not
  negotiable; a hand-drawn SVG eye is a plan violation.
- Every endpoint the app calls is already login-gated. The app must treat a 401
  from any call as "session gone" and return to login rather than showing an
  empty screen.
- `uv run pytest` green and `uv run ruff check server/ tests/` clean at the end
  of every task. Baseline is **394 tests**.
- No new Python runtime dependency.
- `firmware/main/provision.c` and `firmware/main/voice_main.c` are unrelated
  in-progress work and are expected to be dirty. Never stage them.

is near-black glass emitting a cool white, so the neutrals carry a blue bias and

adopts it verbatim so the two pages read as one product.

**Type.** The preview page is monospace throughout — `ui-monospace, "SF Mono",
Menlo, Monaco, monospace` — with tight tracking on headings (`-0.033em`) and
wide tracking on small uppercase labels (`.13em`–`.16em`). Keep all of that for
chrome, labels, numbers and the inspector. **One deliberate deviation:** the
assistant's replies are prose, often Ukrainian or Russian, and monospace
paragraphs of Cyrillic are tiring to read — so reply text alone uses a system UI
stack (`system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`) at 15/1.55.
No webfonts: zero loading, works offline, and matches the preview page.

**Structure.** Mobile-first single column; at ≥900px the face and the inspector
move into a right rail. Messages are blocks with a small mono label above them
(`YOU` / the role's name), not chat bubbles. Numbers are always mono and always
carry their unit.

**The signature element** is the face: a true-black inset panel showing *the
device's own eyes*, played from frames generated by `face.c`, driven by the live
`state` and `emotion` frames. It is the one place colour appears (the cool
`--emit` white on `--glass`), and it is what makes this the playground for this
device rather than a chat window. Everything else stays quiet.

**Quality floor, not negotiable:** keyboard focus visible on every control,
`prefers-reduced-motion` respected (the face holds a still frame), responsive to
320px, and every input reachable with a label.

## Note on this plan's code blocks

The backend plan this follows carried complete code for every step. A frontend
of this size cannot without becoming unreadable, so this plan is explicit where
being explicit matters — API and frame contracts, the WebSocket hook, PCM
conversion, frame decoding, the Dockerfile, the SPA fallback — and specifies
routine markup by structure, behaviour and acceptance instead of transcribing
every element. Where a step says "exactly", it means exactly.

**There is no browser in the implementation environment, and there are no
frontend unit tests in this plan.** Backend changes get pytest as usual. Each
frontend task therefore ends with a **Verify in a browser** block: a numbered
list of what to do and what must happen. The person running the plan performs
it. A task is not complete until that block passes, and an implementer must
report which items they could not check rather than assuming.

## The contract, as it actually shipped

Verified against `server/main.py` and `server/session.py` at commit `cdfe73a`.

**Auth.** `POST /login` `{username, password}` → 200 sets the cookie, 401 on
failure with a generic message. `POST /logout` → 200. Every route below returns
401 without the cookie.

**Roles.** `GET /roles` → array of
`{id, name, prompt, max_sentences, markdown_allowed, languages, pinned_mood, built_in}`.
`POST /roles` takes all of those but `id`/`built_in`; 409 duplicate name, 422 on
a language outside `["uk","ru","en"]`, a mood outside the nine, or a prompt over
**2000** characters. `PUT /roles/{id}` patches only the fields sent — and
`prompt: null` is a real value meaning "revert to the built-in wording", so the
client must distinguish "not sent" from "sent as null". 422 on an explicit null
for `name`, `max_sentences` or `markdown_allowed`; 422 renaming a `built_in`
role; 409 for a duplicate name. `DELETE /roles/{id}` → 409 for a `built_in` one.

**Surfaces.** `GET /settings/surfaces` → `{esp32: <role>, web: <role>}`.
`PUT /settings/surfaces/{esp32|web}` `{role_id}` → 404 for an unknown surface or
role.

**App settings.** `GET /settings/app` → `{store_conversations, retention_days}`.
`PUT /settings/app` with either field.

**Memory.** `GET /memory/{device_id}` → `[{id, text, source, created_at}]` where
`source` is `"auto"` or `"user"`. `POST /memory/{device_id}` `{text}` adds a
standing instruction. `DELETE /memory/{device_id}/{fact_id}`.
`DELETE /memory/{device_id}` drops that device's facts **and** its recorded
conversations. `DELETE /conversations/{device_id}` drops only the transcripts.

**WebSocket `/ws?device=default`.** Client → server:
`{"type":"text","value":"..."}` for a typed question; `{"type":"start"}`, binary
PCM chunks, `{"type":"end"}` for a spoken one; `{"type":"cancel"}` to interrupt.
Server → client: `{"type":"state","value":"idle|listening|thinking|speaking"}`,
`{"type":"emotion","value":"<one of nine>"}`, `{"type":"reply","value":"<one
sentence>"}` (typed questions only), binary PCM (spoken questions only),
`{"type":"done"}`, and:

```json
{"type":"trace","value":{
  "role":"Web default","surface":"web",
  "facts":[{"text":"Lives in Chernivtsi","score":0.7513}],
  "prompt":"<the full assembled system prompt>",
  "prompt_tokens":412,"completion_tokens":18,
  "emotion":"curious","spoken":false,
  "stt_ms":0.0,"reply_ms":845.3}}
```

One `trace` per answered turn, cookie-authorised connections only. **A browser
on an open dev server with no login is labelled `esp32` and receives none** —
if the inspector is empty locally, that is why.

Audio both directions is 16 kHz, 16-bit signed, mono, little-endian raw PCM.

- [ ] **Step 5: Serve the bundle, last, with a fallback that cannot shadow the API**

Still in `server/main.py`: delete the `GET /memory` HTML route, the
`_MEMORY_UI_HTML` constant and its `Path`/`HTMLResponse` imports if now unused,
and `git rm server/static/memory.html`. Then, immediately before `return app`:

```python
    # Registered last, so every API route above wins. The catch-all only
    # answers GETs that look like navigation: anything else, and anything
    # under a known API prefix, must keep returning a JSON 404 rather than
    # an HTML page a fetch() would try to parse.
    _DIST = Path(__file__).parent.parent / "web" / "dist"
    _API_PREFIXES = (
        "login", "logout", "me", "roles", "settings", "memory",
        "conversations", "healthz", "ws",
    )
    if _DIST.is_dir():
        app.mount("/assets", StaticFiles(directory=_DIST / "assets"), name="assets")

        @app.get("/{path:path}", include_in_schema=False)
        async def spa(path: str):
            if path.split("/", 1)[0] in _API_PREFIXES:
                raise HTTPException(status_code=404, detail="not found")
            # Vite emits favicons, manifests and everything else in public/ at
            # the root of the bundle, not under assets/ - so without this, a
            # favicon request gets a 200 of index.html.
            if path:
                candidate = (_DIST / path).resolve()
                if candidate.is_file() and candidate.is_relative_to(_DIST.resolve()):
                    return FileResponse(candidate)
            return FileResponse(_DIST / "index.html")
    else:
        log.warning("web/dist is missing - the API is up but there is no app to serve; "
                    "run `npm --prefix web run build`")
```

Add `from fastapi.responses import FileResponse` and `from fastapi.staticfiles
import StaticFiles`. Keep `Path` imported.

## Task 2: Login, and the shell that knows you are logged out

**Files:**
- Create: `web/src/api.ts`, `web/src/Login.tsx`, `web/src/Shell.tsx`
- Modify: `web/src/App.tsx`

**Interfaces:**
- Produces: `api.get/post/put/del(path, body?)` throwing `Unauthorized` on 401;
  `useSession()` exposing `{state: 'loading'|'in'|'out', username}`, `signIn`,
  `signOut`; `<Shell>` giving every page the same header and tab row.

- [ ] **Step 1: The fetch wrapper**

`web/src/api.ts`. One `request(method, path, body?)` used by thin `get`/`post`/
`put`/`del` helpers. It must:
- send `credentials: 'same-origin'` and `Content-Type: application/json`;
- throw a distinguishable `Unauthorized` error on 401 — every caller relies on
  telling "your session ended" apart from "that was invalid";
- on any other non-2xx, throw an `ApiError` carrying `status` and the server's
  `detail` string, because the roles form must show *why* a 409 or 422 happened
  rather than "something went wrong";
- return parsed JSON, or `null` for 204/empty bodies.

- [ ] **Step 2: Session state**

`useSession()` calls `GET /me` once on mount: 200 → `in` with the username, 401
→ `out`, network failure → `out` with a message. `signIn(username, password)`
posts `/login` then re-probes. `signOut()` posts `/logout` then sets `out`.

Export a helper the rest of the app uses on every failed call: when an
`Unauthorized` is caught anywhere, the app returns to the login view. Wire it
through context rather than by reloading the page — a reload loses whatever the
person had typed.

- [ ] **Step 3: The login view**

`Login.tsx`: a single centred panel, one `--surface` card on `--bg`, product
name in tight-tracked mono, two labelled inputs (username, password, both with
real `<label>`s and correct `autocomplete`), one submit button reading **Sign
in**. On failure show exactly one line: `That username and password did not
match.` — no field-level guessing, since the server deliberately returns one
generic 401. Disable the button while the request is in flight and keep the
typed values on failure.

- [ ] **Step 4: The shell**

`Shell.tsx`: a header carrying the product name and, at the right, the username
and a **Sign out** button. Below it a two-tab row — **Chat** and **Settings** —
as real buttons with `aria-current` on the active one. Tab state lives in
`App.tsx`. On mobile the header collapses to one row and the tabs sit full-width
beneath it.

`App.tsx`: `loading` → a quiet single line, `out` → `<Login>`, `in` →
`<Shell>` wrapping the active tab. Chat and Settings are placeholders this task;
Tasks 3 and 5 fill them.

**Tab state lives in React, not in the URL, and that is a constraint rather
than laziness.** Task 1's SPA fallback refuses any path whose first segment is
an API prefix — `login`, `logout`, `me`, `roles`, `settings`, `memory`,
`conversations`, `healthz`, `ws` — so that a mistyped `fetch()` gets a JSON 404
instead of HTML. Verified: `GET /settings` returns a JSON 404 today. So a
client-side route named `/settings` or `/roles` would 404 on reload, which is
the worst kind of bug: it works until someone refreshes.

Do not add a router in this task. When one is eventually wanted, take one of
these and say which: put client routes under a segment the API does not use
(`/app/settings`), or use a hash router (`#/settings`). Never add a client
route whose first segment appears in `_API_PREFIXES`.

**Verify in a browser:**
1. Create an account — it takes flags, not prompts:
   `uv run python scripts/create_account.py --username you --password <something>`
2. Load the app → the login panel.
3. A wrong password → the single generic line, values retained, button re-enabled.
4. The correct password → the shell, your username in the header.
5. Reload → still signed in (the cookie survives).
6. **Sign out** → back to login. Reload → still login.
7. Narrow to 320px → nothing overflows horizontally.
8. Tab through login and the shell → focus is always visible.

## Task 3: Chat — a typed question, streaming back

**Files:**
- Create: `web/src/useTurn.ts`, `web/src/Chat.tsx`, `web/src/Message.tsx`
- Modify: `web/src/App.tsx`

**Interfaces:**
- Produces: `useTurn()` owning the socket and exposing
  `{connection, state, turns, ask(text), interrupt()}` where a turn is
  `{id, question, sentences: string[], emotion, trace, done}`. Task 4 reads
  `trace`; Task 6 reads `state` and `emotion`.

- [ ] **Step 1: The socket hook**

`useTurn.ts`. One `WebSocket` to `` `${location.origin.replace(/^http/, 'ws')}/ws?device=default` ``,
opened once and kept. Rules that matter:

- **Frame dispatch.** `state` → connection state; `emotion` → the current
  turn's emotion; `reply` → append a sentence to the current turn; `trace` →
  attach to the current turn; `done` → mark it complete. An unknown `type` is
  ignored, not thrown — the server may grow frames before the app does.
- **`reply` frames arrive one sentence at a time** and must render as they
  arrive. Accumulate into an array and join with a space for display; do not
  wait for `done`.
- **Binary frames are audio** and belong to Task 7. Ignore them here, and say so
  in a comment so nobody treats the silence as a bug.
- **Reconnect** with backoff (1s, 2s, 4s, capped at 10s) and surface the
  connection state so the composer can be disabled while it is down. A closed
  socket must not silently swallow a question.
- **A 4401 close means unauthorised** — the cookie is gone. Report that
  distinctly so the app can return to login rather than reconnecting forever
  against a door that will not open.
- `ask(text)` pushes a new turn with the question, then sends
  `{"type":"text","value":text}`. `interrupt()` sends `{"type":"cancel"}`.

- [ ] **Step 2: The message block**

`Message.tsx`. Two shapes, both blocks, no bubbles:
- the question: a wide-tracked mono `YOU` label, then the text;
- the reply: a mono label carrying the active role's name (from the trace, or
  the fallback string `assistant` before the trace arrives), then the sentences
  in `.prose`.

While a reply is streaming and has no sentences yet, show a quiet mono
`thinking…`. When the connection state is `speaking` for a typed question there
is nothing to play — do not show a speaker affordance that does nothing.

- [ ] **Step 3: The chat view**

`Chat.tsx`. A scrolling column of messages with a composer pinned to the bottom:
a `textarea` that grows to a few lines, Enter to send, Shift+Enter for a
newline, and a **Send** button. Disable both while the connection is down, with
one line saying why. Auto-scroll to the newest message **only when the person is
already at the bottom** — yanking the view while they are reading an inspector
panel is worse than a missed scroll.

Empty state, in the interface's voice, not an apology: a short line inviting the
first question, e.g. `Ask it something. Ukrainian, Russian or English.`

- [ ] **Step 4: Wire it into the shell**

The Chat tab renders `<Chat>`. Keep one `useTurn()` instance alive for the whole
signed-in session so switching to Settings and back does not drop the socket or
the transcript.

**Verify in a browser:**
1. Sign in, ask `Привіт, як твої справи?` (mock mode replies without any API key).
2. Sentences appear progressively, not all at once at the end.
3. The reply label shows the active role's name once the trace lands.
4. Ask a second question while the first is still streaming → the first stops and
   the second is answered.
5. Stop the server → the composer disables with a reason. Restart it → it
   reconnects on its own within a few seconds.
6. Scroll up mid-reply → the view stays where you put it.
7. 320px wide → the composer and messages still fit.

- [ ] **Step 5: Commit**

```bash
git add web/src
git commit -m "Answer a typed question, one sentence at a time

The server already streams a typed reply per sentence, so the app renders per
sentence rather than waiting for done - the whole reason that path exists.
Auto-scroll only follows when you are already at the bottom, because being
yanked away from an inspector panel you are reading is worse than a missed
scroll."
```

## Task 4: The inspector — why it answered that

This is the task that makes the app a playground rather than a chat window.

**Files:**
- Create: `web/src/Inspector.tsx`
- Modify: `web/src/Message.tsx`

- [ ] **Step 1: The collapsed strip**

Under every completed reply, one row of mono figures, each with its unit, in
`--ink-2` on `--sunk`: the emotion, `reply_ms`, `prompt_tokens` in, and the
number of facts retrieved. `stt_ms` appears only when it is non-zero — a typed
question has no STT stage and a `0 ms` reading invites the wrong conclusion.
The row is a `<button>` with `aria-expanded`, reading **Why this answer?** when
collapsed.

- [ ] **Step 2: Expanded — the three things worth seeing**

## Task 6: The device's own eyes, in the browser

**Do not draw eyes in JavaScript.** `firmware/host/face_preview.c` already
drives the real `face.c` and encodes frames; this task adds a second, smaller
output from the same source and plays it. If the frames are generated from
`face.c`, the browser and the panel cannot drift; if they are hand-drawn, they
drift within a day, which that file's own header records.

**Files:**
- Create: `firmware/host/face_export.c`
- Modify: `firmware/host/Makefile`
- Create: `web/src/face-frames.json` (generated, committed)
- Create: `web/src/Face.tsx`
- Modify: `web/src/Chat.tsx`

- [ ] **Step 1: Export the frames the web app needs**

`face_export.c` links `../main/face.c` exactly as `face_preview.c` does, and
writes JSON to stdout: for each of the four states the browser can be in
(`idle`, `listening`, `thinking`, `speaking`) crossed with the nine emotions,
a short loop of frames — enough to carry a blink and the state's motion, at the
25 fps `face_preview.c` uses.

Each frame is the 1024-byte framebuffer in the panel's own layout (8 pages ×
128 columns, bit *n* of a byte being row `page*8+n` — `face.h` says so), encoded
as base64 so the file stays a reasonable size. Emit `{"w":128,"h":64,"fps":25,
"loops":{"<state>:<emotion>":["<base64>", …]}}`.

Keep the loops short — a second or two each. This file is committed, so its size
is a cost paid on every clone; report what you get and trim the loop lengths if
it exceeds about 1.5 MB.

Add to `firmware/host/Makefile`, following the existing `face_preview` pattern:

```make
$(BUILD)/face_export: ../main/face.c ../main/face.h face_export.c | $(BUILD)
	$(CC) $(CFLAGS) -o $@ ../main/face.c face_export.c

face-data: $(BUILD)/face_export
	@./$(BUILD)/face_export > ../../web/src/face-frames.json
	@echo "wrote web/src/face-frames.json"
```

Add `face-data` to `.PHONY`. Do **not** add it to `all`: the frames change only
when `face.c` does, and a frontend build should not require a C compiler.

Run: `make -C firmware/host face-data`
Then: `make -C firmware/host test`
Expected: the export writes the file, and the existing face tests still pass —
you have added a consumer of `face.c`, not changed it.

- [ ] **Step 2: Play it**

`Face.tsx`: a `<canvas>` at 128×64 scaled up with `image-rendering: pixelated`,
inside a panel using `--glass` for the ground and `--emit` for lit pixels, with
the `--grid` overlay the preview page uses. Decode the base64 for the current
`state:emotion` loop, unpack bits in the panel's layout, and step frames on a
`requestAnimationFrame` clock at the file's `fps`.

Requirements:
- switching state or emotion switches loops at the next frame boundary, not
  mid-frame;
- `prefers-reduced-motion` holds the first frame and does not animate;
- when the socket is down, show the `idle` loop and mark the panel with a mono
  `offline` label in `--ink-3` rather than freezing on a stale expression;
- unpack once per frame into a reused `ImageData`, not per pixel per render.

- [ ] **Step 3: Place it**

Above the transcript on mobile; in a right rail beside it at ≥900px, sticky so
it stays visible while scrolling. Under the panel, one wide-tracked mono line:
the state, and the emotion when one has been chosen.

**Verify in a browser:**
1. Ask a question → the eyes move through thinking and settle on the reply's
   emotion, and the label agrees with the inspector's `emotion`.
2. Pin a mood to the browser's role, ask again → the eyes show the pinned mood.
3. Compare against `make -C firmware/host preview` → the same eyes, not an
   approximation.
4. Stop the server → `offline`, idle eyes.
5. Reduce motion → a still frame, no animation.
6. 320px → the panel scales down and the transcript is still usable.

- [ ] **Step 4: Commit**

```bash
git add firmware/host/face_export.c firmware/host/Makefile web/src/face-frames.json web/src/Face.tsx web/src/Chat.tsx
git commit -m "Give the browser the device's eyes, generated from the device's code
```

## Task 7: Voice — speak to it, hear it back

Text is the primary surface; this is the optional half, last on purpose. If it
slips, everything above still ships.

**Files:**
- Create: `web/src/audio.ts`, `web/src/Mic.tsx`
- Modify: `web/src/useTurn.ts`, `web/src/Chat.tsx`

- [ ] **Step 1: Capture at the rate the protocol wants**

`audio.ts`. `getUserMedia({audio: {channelCount: 1, echoCancellation: true,
noiseSuppression: true}})`, then an `AudioWorklet` (not the deprecated
`ScriptProcessor`) producing Float32 frames. Ask for an `AudioContext` at
16000 Hz; browsers may refuse and give 48000, so **resample explicitly** rather
than assuming — and if you must resample, average whole groups of samples rather
than picking every third one, which aliases audibly. Convert to 16-bit signed
little-endian:

```ts
export function floatTo16LE(input: Float32Array): ArrayBuffer {
  const out = new DataView(new ArrayBuffer(input.length * 2))
  for (let i = 0; i < input.length; i++) {
    const s = Math.max(-1, Math.min(1, input[i]))
    out.setInt16(i * 2, s < 0 ? s * 0x8000 : s * 0x7fff, true)
  }
  return out.buffer
}
```

Send `{"type":"start"}`, then binary chunks **while recording** — the device
streams as the button is held and the server expects the same — then
`{"type":"end"}`. Do not buffer the whole utterance and send it at the end;
`SESSION_TIMEOUT_S` also caps how much one utterance may buffer.

- [ ] **Step 2: Play the reply**

A spoken question is answered with **binary PCM frames**, not `reply` text.
Queue them and play through an `AudioContext`, appending as they arrive so
playback starts before the reply finishes — that pipelining is the whole latency
argument of this project. Handle `done` as end-of-reply. A gap in arrival must
not end playback early.

- [ ] **Step 3: The control**

`Mic.tsx`: a press-and-hold button, mirroring the device's own gesture, with a
keyboard-accessible equivalent (space while focused) and a visible recording
state. Show the microphone-permission denial as a line telling the person how to
fix it, not as a dead button. Disable it while a reply is playing, or make
pressing it interrupt — pick one, and make the label say which.

**Verify in a browser:**
1. With real keys, hold the button, ask something aloud, release → a spoken
   reply plays, and the first audio starts before the whole reply is ready.
2. The inspector shows a non-zero `stt_ms` for that turn.
3. Deny microphone permission → a line explaining how to grant it.
4. Interrupt a spoken reply → it stops.
5. On a phone on your LAN, with `SESSION_COOKIE_SECURE=False`, the same flow
   works. Note that browsers require HTTPS or localhost for microphone access,
   so expect to need `localhost` or a tunnel; record what you found.

- [ ] **Step 4: Commit**

```bash
git add web/src
git commit -m "Let the browser hold the button too

Same framing the device uses - 16 kHz mono PCM, streamed while recording rather
than buffered and posted - so the browser is another device on one protocol
instead of a second one. Playback appends as frames arrive, because starting
before the reply is finished is the entire latency argument of this project."
```

## Self-Review

**Spec coverage.** Every frontend item in
`docs/superpowers/specs/2026-09-01-playground-slice-1-design.md` maps to a task:
React+Vite as the first build step in the repo (T1), the static mount and SPA
fallback (T1), retiring the old memory page (T1), login and the cookie (T2),
streaming chat through the existing pipeline (T3), the inspector (T4), the
settings page covering persona/style plus the memory list/add/delete (T5),
mobile-first throughout (every task's verification ends at 320px), voice using
the same audio framing as the device (T7), the Dockerfile and
`SESSION_SECRET_KEY` (T1, T8), and the post-deploy cleanup of other people's
facts (T8).

**Beyond the spec, deliberately:** `GET /me` (T1) — the spec assumed a session
probe existed and none did; and the face (T6), which the spec did not mention.
The face is justified by the spec's own founding decision that the device and
the browser are one assistant, and by `face_preview.c` having already built the
machinery. It is Task 6 of 8, so it cannot block anything.

**Not in this plan:** document RAG (slice 2), the dashboard that reads the
recorded conversations (slice 3), MCP (slice 4), real-time cross-surface sync,
passkeys, a PWA shell.

**Known weakness, stated rather than hidden.** There are no automated frontend
tests here, so the safety net is the per-task browser checklist and a person
running it. That is thinner than the backend's 394 tests. If this app grows past
slice 1, a component test harness is the first thing to add — and the WebSocket
hook in T3 and the PCM conversion in T7 are the two places where a test would
have paid for itself soonest.

**Type consistency.** `api.ts`'s `Unauthorized`/`ApiError` (T2) are what T3's
socket and T5's forms both handle. `useTurn()`'s turn shape (T3) is what T4's
inspector and T6's face read; the field names match the `trace` payload
documented above. The role JSON in T5's forms matches `_role_json` exactly,
`built_in` included.
